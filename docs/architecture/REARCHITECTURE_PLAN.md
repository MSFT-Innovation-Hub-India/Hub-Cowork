# Hub Cowork — Rearchitecture Plan

> **Goal:** Bring the existing codebase into full compliance with [`SKILLS_DESIGN_PRINCIPLES.md`](SKILLS_DESIGN_PRINCIPLES.md). Make Hub Cowork a clean reference implementation of the Claude-Cowork-style skills-based architecture, on Azure OpenAI Responses API + local Python tools.
>
> **Status — largely landed.** The major structural phases of this plan are complete in `main`:
>
> - ✅ Per-skill folders with `skill.yaml` (config) + `SKILL.md` (expertise) — see [`AUTHORING_A_SKILL.md`](AUTHORING_A_SKILL.md).
> - ✅ The 4-phase `hub_agenda_creation/{briefing,goals,build,publish}.yaml` chain has been collapsed into the single `engagement_agenda` skill. `next_skill` chaining and the on-disk `engagement_context` JSON store are gone.
> - ✅ `[STOP_CHAIN]` / `[AWAITING_CONFIRMATION]` marker parsing has been removed from `agent_core`. HITL is now driven by the thread-status flag.
> - ✅ Tools have moved to MCP servers under `mcp_servers/` (shared) and `skills/<skill>/mcp_server/` (skill-local). The `MCPClientPool` in [`core/mcp_client_pool.py`](../../src/hub_cowork/core/mcp_client_pool.py) lazily spawns each as a stdio subprocess and multiplexes calls. The host registers MCP tools with the Azure OpenAI Responses API as ordinary `type="function"` tools (stdio MCP servers cannot be passed as native `mcp` tools — that mode requires a remote HTTP URL).
> - ✅ `previous_response_id` is the single conversation-state primitive. The `thread.messages` mirror has been removed.
>
> **Outstanding cleanups (Phase 5 / cosmetic):**
>
> - 🟡 Some `skill.yaml` files still use the legacy field name `model: full|mini` rather than the design-doc target name `model_tier: reasoning|fast`. Both load identically — rename pending.
> - 🟡 `run_agent_on_thread` and `run_skill_on_thread` are still separate functions in `agent_core`. The design doc collapses them to one. Pending.
> - 🟡 ACA-hosted streamable-HTTP transport for one or more shared MCP servers — not started; will be a one-line `skill.yaml` change per server when triggered.
>
> The historical sections below are kept verbatim as audit trail. Backup of pre-overhaul state: `MSFT-Innovation-Hub-India/backup_hub_cowork`.

## What's wrong today

| Symptom | Today | Target |
|---|---|---|
| Instructions inline in YAML, ~150 lines per skill, full of step-by-step procedure | `engagement_briefing.yaml`, `engagement_agenda_publish.yaml`, etc. | `skill.yaml` (config) + `SKILL.md` (expertise) |
| Multi-phase workflow split into 4 chained skills with `next_skill` + `engagement_context` JSON handoff | `hub_agenda_creation/{briefing,goals,build,publish}.yaml` | One `engagement_agenda` skill, smarter tools |
| `[STOP_CHAIN]` / `[AWAITING_CONFIRMATION]` markers parsed from model text | `agent_core.py` lines ~788–830 | Removed. HITL = thread-status flag set when API returns final text without tool calls |
| Procedural string formatting in instructions (filename, table layout, link extraction) | All four agenda phases | Moved into tool code |
| Tools that hardcode user-facing error prose | `engagement_context.py` returns of "No agenda content found …" | Tools return `{"found": false, ...}` JSON; model writes the prose |
| Custom tool-call loop in `agent_core` that re-implements what Responses API does | `run_skill_on_thread` (large) | Thin mechanical bridge: ~30–50 lines |
| `conversational: true/false` flag, per-thread message history maintained outside Responses API | `ConversationThread.messages` | Removed. `previous_response_id` is the single source of conversation context |

---

## Guiding constraints

1. **Tools migrate to MCP servers (stdio, host-managed).** Per-skill MCP servers ship inside each skill folder; cross-cutting tools live in shared servers under `src/hub_cowork/mcp_servers/`. The host's `MCPClientPool` spawns each server lazily and keeps it warm. Future move to Azure Container Apps is a transport swap, not a rewrite. (Per design doc §8, §11, §11A, §18.5.)
2. **No UI rewrite.** WebSocket protocol stays. The chat UI doesn't need to know skills collapsed.
3. **No new external dependencies** beyond what's already in `requirements.txt`.
4. **Reversible by phase.** Each phase ships a working agent. We never go through a long broken-master period.
5. **The 4-phase agenda workflow is the canary.** It is the most complex skill and the worst offender. If the new design works for it, it works for everything.

### Phase 1 — Split `instructions:` out of YAML into `SKILL.md` (no behavior change)

For every existing skill: extract the `instructions:` block into a sibling `SKILL.md` file. The skill loader is taught to read `SKILL.md` if present and fall back to YAML `instructions:` otherwise.

**Steps:**

1. Update `_load_skills()` in `agent_core.py`: when loading a YAML, look for `SKILL.md` next to it; if present, that becomes the system prompt and YAML `instructions:` is ignored (warn if both exist).
2. For each of the 9 skills, create `SKILL.md` with the existing instructions verbatim and delete the `instructions:` field from the YAML.
3. Skills become folders where they are currently flat files (e.g., `qa.yaml` → `qa/skill.yaml` + `qa/SKILL.md`).
4. Restart and verify all skills still work end-to-end (manual smoke test through the UI).

**Outcome:** Same behavior, cleaner files. Designers can edit prompts as Markdown. No model / runtime changes yet.

**Risk:** Low. Pure file refactor.

---

### Phase 2 — Strip control-flow markers and `next_skill` from runtime

This phase removes the `[STOP_CHAIN]` / `[AWAITING_CONFIRMATION]` parsing and `next_skill` chaining from `agent_core.py`. HITL becomes a natural-conversation pattern.

**Steps:**

1. **Runtime change:** in `agent_core.py`, replace marker-parsing block (~lines 780–830) with this rule:
   - If the API returns a final text response and the message is a question / asks for clarification, set `thread.status = "awaiting_user"` and surface the text. (Heuristic: any non-tool final response while we're mid-workflow is HITL by definition; no special detection needed.)
   - If the API returns a final text and indicates completion, set `thread.status = "complete"`.
   - There is no chain. There is no `next_skill`.
2. **Skill changes:** in every `SKILL.md`, delete `[STOP_CHAIN]` and `[AWAITING_CONFIRMATION]` directives and the prose around them. Replace with natural language: *"If no briefing calls are found, tell the user and stop."* / *"Confirm the selection with the user before proceeding."*
3. **YAML changes:** delete `next_skill:` from all chained skills. Delete `conversational:` everywhere — every skill is conversational by default now.
4. **Smoke test** the agenda workflow manually. The 4 phases still exist as separate skills *for now* — we keep them chained via the model's natural sequencing, even though they're separate skills, by routing each phase as the user hits it. This is a temporary state — Phase 3 collapses them.

**Outcome:** No state-machine code in `agent_core`. HITL works through thread status only. Errors flow as ordinary conversation messages.

**Risk:** Medium. Some SKILL.md prose needs careful rewriting so the model still asks for confirmation reliably. Test on the briefing skill first.

---

### Phase 3 — Collapse the 4-phase agenda chain into one skill

This is the canary skill. It validates that one skill + smart tools + Responses API loop can replace four chained skills + control markers + JSON-on-disk handoff.

**Steps:**

1. **Audit each phase's instructions** and split into:
   - **Domain knowledge** → goes into the new unified `engagement_agenda/SKILL.md`.
   - **Procedure** → goes into a tool.
2. **New / refactored tools:**
   - `find_briefing_calls(customer)` → wraps the WorkIQ query, returns structured `[{title, date, organizer, participants, kind: internal|external}, ...]`.
   - `retrieve_briefing_notes(meeting_ids: list[str])` → returns `{internal_notes, external_notes}` (full text, no summarization).
   - `extract_engagement_metadata(notes)` *(optional)* — if classification turns out to be flaky in pure prompt, do a focused mini-model call inside this tool; otherwise let the orchestrator model classify directly from `SKILL.md` rules.
   - `build_agenda(metadata, goals, hub_config)` → returns `{agenda_markdown, time_slots, ...}`. Owns time math, speaker mapping, table layout.
   - `publish_agenda_doc(customer, agenda_markdown, metadata)` → builds filename internally, calls `create_word_doc`, returns `{filename, path, open_link}`.
3. **Delete** `engagement_context.py` and the `engagement_context/` JSON store. Phase-to-phase context flows via `previous_response_id`.
4. **Delete** the 4 phase YAMLs and 4 phase SKILL.mds; replace with one `engagement_agenda/skill.yaml` + `engagement_agenda/SKILL.md`.
5. **Restart and exercise** the full workflow on a real customer end-to-end.

**Target shape of `engagement_agenda/SKILL.md`:** ≤150 lines, all expertise, zero procedure. (Compare to the ~600 combined lines today.)

**Risk:** High. This is where the model's autonomy is being tested for the first time on a complex workflow. Have backup_hub_cowork ready as the fallback.

---

### Phase 4 — Thin the `agent_core` loop

With markers and chaining gone, `run_skill_on_thread` is now mostly: call API → execute tools → call API → return final text. Cut everything else.

**Steps:**

1. Replace the bespoke loop with the canonical Responses API tool-execution bridge (~30–50 lines):
   ```python
   response = client.responses.create(...)
   while response.status == "requires_action":
       outputs = [execute_tool(tc) for tc in response.required_action.tool_calls]
       response = client.responses.create(previous_response_id=response.id, tool_outputs=outputs)
   thread.previous_response_id = response.id
   return response.output_text
   ```
2. Drop `_responses_client` token-refresh ad-hoc code into a small helper module; keep only the lock + refresh, not the loop logic.
3. Delete `ConversationThread.messages` — `previous_response_id` is the only conversation context now.
4. Drop `run_agent_on_thread` vs `run_skill_on_thread` distinction; one function dispatches both routing and execution.

**Outcome:** `agent_core.py` shrinks by ~50%. No decisions made in code.

**Risk:** Low–medium. Mechanical refactor once Phase 3 is green.

### Phase 7 — Migrate tools to MCP servers (stdio, host-managed)

With skills clean and the runtime thinned, repackage every tool as an MCP server. The model sees no change — same JSON-schema function tools through the Responses API — but the boundaries snap into Cowork's shape and ACA hosting becomes a one-line swap later.

**Steps:**

1. **Add `mcp` to `requirements.txt`.** Pin to a recent stable release of the official Python SDK.
2. **Build `core/mcp_client_pool.py`.** A small singleton in `agent_core` that:
   - Resolves a server name to either a Python module path (stdio) or an HTTP URL (future).
   - Lazy-spawns one stdio subprocess per server name on first use; keeps it warm.
   - Multiplexes all calls to the same server over one MCP session.
   - Forwards MCP `notifications/progress` and `notifications/message` to `on_progress` (tagged via `current_thread_id`).
   - Surfaces server crashes as `{"status": "error", "reason": "mcp_server_crashed"}` and respawns on the next call.
   - Sends MCP `shutdown` and SIGTERM on host exit.
3. **Stand up shared servers under `src/hub_cowork/mcp_servers/`:**
   - `workiq/` — `query_workiq`, `resolve_speakers`, `get_task_status`.
   - `m365/` — `send_email`, `create_word_doc`, `share_onedrive_document`.
   - `progress/` — `log_progress`, `get_hub_config`.
   Each is a FastMCP app with a `__main__.py` so `python -m hub_cowork.mcp_servers.<name>` works as the spawn command.
4. **Stand up per-skill servers** under `src/hub_cowork/skills/<skill>/mcp_server/` for any tool used by exactly one skill (`engagement_agenda`'s `find_briefing_calls`/`build_agenda`/`publish_agenda_doc`, RFP scoring tools, `shelf_watch`'s comparison tool, etc.).
5. **Replace each `SCHEMA: dict` + `handle()` module** with a `@mcp.tool(...)`-decorated function in the right server. Inputs become typed function parameters; the JSON schema is auto-generated by FastMCP.
6. **Update `skill.yaml`** in every skill: replace the loose `tools:` list with `mcp_servers:` (list of shared server names plus `.` for the skill's own server) and an optional `tool_allowlist:` filter.
7. **Replace the in-process tool dispatch** in `agent_core` with `pool.call(server, tool_name, arguments)`. The Responses API is still given **function tools** (`type="function"`) built from each server's MCP `tools/list` advertisement — stdio MCP servers cannot be registered as native `mcp` tools because that API mode only accepts remote HTTP URLs (per design doc §11.4a). Tool execution still happens inside the canonical `while requires_action` loop — only the dispatcher changes.
8. **Verify auth across the boundary.** Each server calls `get_credential()` itself; the shared on-disk MSAL cache makes silent refresh work. Smoke-test each shared server end-to-end after sign-in.
9. **Delete the old `src/hub_cowork/tools/` and `skills/<skill>/tools/` trees** once every tool has moved.

**Outcome:** Tools are MCP servers — per Cowork — with one process for the user to launch and a clean transport swap available for ACA.

**Risk:** Medium. Subprocess pool needs careful lifecycle handling (graceful shutdown, crash recovery, no spawn-per-call). Auth-across-the-boundary is the part most likely to surprise — verify silent token refresh works from a fresh subprocess before declaring a server ready.

**Follow-up (separate effort, not in this plan):** lift one or more shared servers to Azure Container Apps. Change `transport: stdio` to `transport: streamable_http` + `url: ...` in the consuming `skill.yaml`. No skill, tool, or agent-loop code changes.

## Out of scope (explicitly)

- ACA-hosted MCP servers (HTTP/SSE transport). Phase 7 below adds the in-host stdio MCP layer; the move to ACA is a follow-up that swaps `transport: stdio` → `transport: streamable_http` in `skill.yaml` (§11.7).
- Server-side tool execution via Foundry. (Future, when local-first stops being a hard constraint.)
- Replacing pywebview. (Decided: it's the right stack.)
- **Per-conversation concurrency** — `ThreadManager`, `ExecutorPool`, `ConversationThread`, `LocalJsonThreadStore`. Multiple chat threads run independently in parallel today and continue to do so. Each thread keeps its own `previous_response_id`; the new `MCPClientPool` is host-scoped and shared across threads (one warm subprocess per server, multiplexed). No phase touches threading. (§9b contract in design doc.)
- **Desktop host and chat UI** — `host/desktop_host.py`, `assets/chat_ui.{html,js,css}`, the WebSocket protocol on 18080, the HTTP server on 18081, the tray icon, request-id correlation. The rearchitecture is server-side only; no UI changes, no protocol changes. (§9b contract.)
- The Teams / Redis bridge. It's orthogonal to the skills layer and stays as-is.
- Per-skill model routing (`reasoning` vs `fast`). It stays — it's a Hub-Cowork strength over Cowork.
- **Authentication and credential management.** `core/auth_credential.py` (WAM broker `InteractiveBrowserBrokerCredential` parented to the pywebview HWND, classic `InteractiveBrowserCredential` fallback), shared-credential pattern via `set_credential()` / `get_credential()`, `AuthenticationRecord` silent-refresh, the MSAL cache name `hub_cowork`, and the Settings-UI Sign-In flow. **Do not refactor.** Every phase below leaves auth wiring untouched — `agent_core`'s thinning in Phase 4 keeps the credential/`OpenAI` client construction and the `_responses_client_lock` token-refresh path exactly as they are today. Phase 7's MCP migration uses the same shared on-disk MSAL cache: each server subprocess calls `get_credential()` itself and gets silent-refresh tokens from the same cache the host populated at sign-in.

## Decision points the user needs to confirm before Phase 3 ships

1. **Single classifier model call vs. mega-prompt with all skills loaded.** Today: separate cheap classifier call. Recommend keeping it for the per-skill model-tier routing benefit.
2. **Whether `extract_engagement_metadata` becomes its own tool with an internal mini-model call**, or stays in the orchestrator's prompt. Decide after testing — start with prompt, escalate to a tool only if the model misclassifies.
3. **Where to store transient state during a single agenda run.** `previous_response_id` covers it for one user thread. If we ever need a "resume an abandoned agenda from yesterday," we'd reintroduce a context store — but only at that point, not preemptively.
